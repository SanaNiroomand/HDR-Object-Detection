Phase 1 — Auditing the dataset

Every one of the 4,080 EXR files was decoded and measured. No sampling.

01

Checked that the labels are trustworthy

All 4,080 images decoded with zero read failures. The two label formats — plain text files and COCO JSON — agree exactly on all 32,964 boxes, class by class. Image dimensions match the JSON in every case.

Only 47 boxes (0.14%) extend past the image edge, and 6 label files are empty. No zero-size boxes.

Result

Annotation quality is good. Nothing here needed fixing.

02

Confirmed the two brightness conventions across the whole set

Earlier work on ~400 files found two groups: files whose maximum value is exactly 255, and files whose maximum is exactly 65504. That holds across all 4,080 — 2,776 and 1,302 files respectively, plus 2 stragglers.

03

Found that neither ceiling is over-exposure

Sampling 120 images from each group, the fraction of pixels actually sitting at the ceiling is around 0.00001% — roughly one pixel per image. Each image was individually scaled so its single brightest sample lands on the ceiling.

Correction to a prior assumption

Nothing is clipped, so there are no blown highlights to recover, and the stored values carry no absolute brightness meaning.

04

Discovered the dataset is three sources glued together

Reading the EXR file headers directly revealed hidden metadata — whiteLuminance, LUMINANCE, and the original filename — that cleanly separates the dataset into three groups.

This matters because S1 and S2 share the same maximum value while being otherwise unalike — so the "two groups" split is not the useful one. The source boundary is.

05

Tested whether the built-in brightness tag fixes the scale gap

The whiteLuminance field looks like exactly the right tool for putting all three groups on one physical scale. It is not: it equals 1.0 for S1 and S2 and only carries real values for S3, so multiplying by it widens the spread from 3.34 to 4.62 decades.

06

Found negative pixel values in 41% of images

1,672 images contain negative brightness values, down to −872 — leftovers from colour processing. Any logarithm or gamma step must clamp these to zero first or it produces invalid numbers on nearly half the dataset.

07

Identified a separate population of very dark scenes

303 images (7.4%) sit in a cleanly separated cluster, with a real gap in the histogram. They are roughly 250× darker than the rest and hold 13.1% of all annotated boxes.

Consequence

Any single brightness curve tuned on the main population will crush these to black — and they are too large a share of the labels to ignore.

08

Measured the dynamic range of every scene

Median 4.11 decades — about 13.7 photographic stops — with a maximum of 7.83 decades (26 stops). This is genuinely wide-range data, and the per-image figures now exist for all 4,080 files, which makes it possible to sort results by scene difficulty later.

09

Quantified the train/test leakage

S3's original filenames are sequential video frames (000001.exr–001499.exr). The dataset's own train/test split was drawn randomly over individual frames, so consecutive near-identical frames land on opposite sides.

Problem found

100% of S3's test frames have a training frame within ±3, and 91% have one immediately adjacent. S3 is about a third of the test set.

10

Characterised the detection task

Class imbalance is 6,084:1 — person, bottle and car account for 86% of boxes, while cat has 3 instances and bus has 7. cow and cat have zero test instances, so their score is undefined and any 20-class average silently depends on how the scoring tool handles that.

Objects are large: median 7.2% of the image side, with only 0.7% qualifying as tiny. That is the opposite profile to traffic datasets, where small distant objects dominate.

Phase 2 — Diagnosing why the previous attempt failed

Two independent bugs, both silent, both invalidating earlier conclusions.

11

Read the RAOD source and found it tone-maps internally

RAOD's first network layer is a learned tone-mapping module: it applies x^(1/gamma) with gamma learned in the range 7–10.5, plus a per-pixel tone curve, then rescales. It is designed to receive dark, linear, untouched input and brighten it itself. RAOD's own data sits at mean 0.0118.

12

Found the missing scaling step in the evaluation script

The data loader divides pixel values by 255 inside load_image, so the network expects values between 0 and 1. The evaluation script skipped that step and fed values up to 255.

The trap: the same division appears commented out in ValTransformRaw — the obvious place to look — because it has already happened one level up. Anyone reimplementing the preprocessing reasonably concludes it should not be applied.

Proved it

RAOD's own sample image produced 0 detections. After restoring one line, the same image produced 5, including a car at 0.892 confidence. Every earlier "this method does not work" result was measured through this.

13

Found the converter was aiming at the opposite target

The previous converter stretched each image to fill the full 0–255 range, landing at mean 0.377 — 32× brighter than anything the model saw in training. Every variant tried (p99, adaptive percentile, log, histogram matching) shares that same "use the full range" goal, so all of them miss in the same direction.

14

Settled the class mapping from source

All three checkpoints have 5-class output heads. The 6-class line in RAOD's annotation script is commented out — Tricycle was dropped. Only person → Pedestrian and car → Car map honestly, covering 64.9% of boxes across 3,818 images.

15

Caught a coordinate trap before it cost anything

RAOD squashes images to 1280×1280 without preserving aspect ratio, and squashes the boxes to match by scaling each axis independently. Reproducing one without the other misaligns every box, with no error message.

Phase 3 — Rebuilding the pipeline

New converter, annotations, splits, evaluation and visualisation tools.

16

Built a leakage-free split

S3's video frames were grouped into 24 contiguous blocks, assigned whole, with a guard band of dropped frames at every boundary. Verified: 0 test frames within ±3 of a training frame, against 252 of 276 in the original split. Both splits were kept so the two can be compared.

17

Wrote a converter that does no tone mapping

Reads the EXR, clamps negatives, converts colour order, resizes with the same aspect-squashing RAOD uses, applies grey-world white balance, and writes the values through with no stretching. All 3,818 usable images converted in 351 seconds, zero failures, about 60 GB.

18

Measured the right brightness level instead of guessing

Phase 4 — Baseline before training

20

Measured the untrained model on the clean split

mAP 0.0590, AP50 0.1277, on 779 test images. Pedestrian AP50 was 0.018 — effectively blind, despite person being 85% of the boxes — while Car reached 0.237.

Phase 5 — Fine-tuning

Three attempts. The first two were abandoned for the same hidden reason.

21

Hit a memory limit that Windows never reports

The first run projected an 8-day completion time with no error of any kind. Measuring memory rather than timing found the cause: batch size 8 needs 17.51 GB on a 17.1 GB card. Windows does not raise an out-of-memory error — it pages GPU memory to system memory, so the run merely becomes slow and erratic.

The second run, at batch 4, still projected 16 hours. Same cause: the scale augmentation was sampling input sizes up to 1600×1600, which needs 22.67 GB.

Phase 6 — Checking whether the result is trustworthy

23

Confirmed no test image was used in training

Verified directly: 0 images appear in both the training and test sets.

24

Measured how much genuinely distinct material the training set holds

2,994 images, but S3's 949 of those are frames from one video in only 6 contiguous runs. Counting near-identical frames once gives roughly 2,051 distinct scenes — about 1.7% of a standard detection training set.

Interpretation

The good result is not explained by an extensive dataset. It is better explained by an easier task — two classes, large objects — plus a strong pretrained starting point.

25

Trained a second model to measure the leakage cost properly

An earlier attempt to measure this compared one model against two test sets, which was invalid — 26% of the original test set was inside that model's training data. The correct design is two models with identical settings, each tested on its own split, compared video-source to video-source so content stays constant.

Phase 7 — Positioning against the literature

27

Established that the headline number is not comparable to TMO-Det

TMO-Det uses the same underlying dataset, but filters out near-identical video frames down to 1,491 training and 380 test images, evaluates all 20 classes with RetinaNet at 1024×576.

Placing 34.9 next to 32.1 would be invalid: this work detects 2 classes, theirs detects 20, including categories with a handful of instances that drag any average down. The tasks are not the same difficulty.

Open scientific question

Their table shows raw HDR performing worst, below plain LDR. RAOD claims the opposite for HDR with a learned adjustment. Both can hold — HDR may hurt when handed over raw and help when the network learns the compression. Nobody has compared the two approaches on the same benchmark.

Phase 8 — Holding the detector fixed, changing only the tone map

Prompted by review comments: the earlier comparison varied the detector and the input at once, so it could not separate them. Scores in this phase are ×100 and cover all 20 classes.

29

Ruled out mmdetection, and pivoted

The intended detector needed mmcv, which requires compiled CUDA extensions. Neither a CUDA toolkit nor a C++ compiler is installed here, and its prebuilt packages stop at PyTorch versions predating this GPU's architecture, so no combination works without a multi-gigabyte toolchain.

Result

Switched to torchvision: no compilation, and it supplies both a one-stage detector (RetinaNet, the family the thesis used) and a two-stage one. Better suited to the question anyway.

30

Chose the tone-mapping operator by measurement, to avoid rigging the comparison

A weak operator would have made the comparison arm lose by construction. Eight candidates were scored with a COCO-pretrained detector, needing no training. The spread was 10% relative, so the choice genuinely mattered; gamma at the 99th percentile won. Every tone-mapped row of the detector comparison uses it, including the fine-tuned Faster R-CNN in Steps 31 and 41. It is not the Reinhard image set built in Step 33.

31

Found an off-the-shelf detector already matches the fine-tuned model

A COCO-pretrained detector with no training on this dataset at all reached AP50 60.6, against fine-tuned RAOD's 61.3. After fine-tuning it reached mAP 51.7 in half an hour, against RAOD's 34.9 in 4.6 hours.

Interpretation

Not evidence that RAOD is wrong: 44M parameters against 1M, and pretraining that covers person and car directly. Both advantages are unrelated to HDR. It does move the burden of proof onto the HDR pipeline.

32

Rebuilt the labels for all 20 classes

Earlier work kept only person and car, because RAOD's head has 5 fixed traffic classes. With a freshly initialised head there was no reason to discard 35% of the boxes, and the thesis tables this sits beside report over 20 classes. Result: 3,229 training and 845 test images, 25,758 and 7,034 boxes. Two classes (cat, cow) have no test instances and drop out of the average.

33

Built five tone-mapping front ends from the same source

Raw HDR with no curve, gamma, log, Reinhard and Durand — identical geometry and white balance, differing only in the curve. Four also appear in the thesis tables, which is what makes any cross-checking possible.

Reinhard here is the global variant (one curve applied uniformly), not the local dodge-and-burn form. The thesis lists both separately elsewhere but does not say which its HDR4RTT table used, so those two rows may not be the same operator. Durand is local in both.

Implementation fault found and fixed

The first Durand implementation was washed out and colour-cast: a gamma was applied on top of an already display-referred result, and the operator was normalised twice. Fixing it exposed a real property of the method — a small very bright source is high-frequency, so it lands in Durand's detail layer and escapes the base compression, leaving the rest of the frame dark. That is the operator behaving as designed, and part of what the comparison measures.

34

Wired RAOD's learned module to the same detector

RAOD publishes its tone-mapping module bolted to a 1M-parameter detector. Putting it in front of the same 38M detector the fixed operators feed separates the module's contribution from the detector's capacity. Weights were initialised from RAOD's released checkpoint. Memory was measured before committing: 13.1 GB of a 17.1 GB card at batch 4.

36

Retested the learned module three more ways

Two settings used could have suppressed it rather than the method being weak, so each was isolated: full learning rate (36.1), random initialisation instead of RAOD's weights (35.7), and input rescaled to the level those weights were fitted at (34.4).

Result

No variant reaches Reinhard, gamma or Durand, so the finding is not an artefact of the settings. The full-learning-rate run does edge log compression, 36.1 against 35.9, too small a margin to read anything into. The rescaling variant was worse, not better — the assumed input-scale mismatch was not the limiting factor.

37

Recorded a failed bridge between the two experiments

The plan was to use the operators common to both experiments to map the thesis's scale onto this one, so its method, which had not been re-run here, could be placed. It does not work: the rankings invert — Reinhard is the worst tone map in the thesis table and the best here. No scale factor reconciles them.

What does hold is comparing each learned method against the best classical operator in its own experiment: the thesis method +0.3 ahead of its best classical, RAOD's module -2.8 behind its own. An indirect comparison, not a head-to-head.

Phase 11 — Where the detector fails, and input geometry

1–2 September. Reinhard + RetinaNet, deduplicated split.

42

Classified every prediction and every missed object

Of predictions above 0.3 confidence: 58.8% correct, 18.8% find the object but draw a poor box, 15.2% land on background, 4.6% have the wrong class, 2.6% are duplicates. 38% of real objects are missed entirely. Each object was joined to statistics measured from the original EXR file.

43

Found that misses follow local contrast, not darkness

Holding object size fixed (objects 5–10% of the image side), objects with under 1 decade of brightness range inside their own box are missed 66% of the time; those with over 3 decades, 12%. Flat, low-contrast objects are the hard ones.

Interpretation

Every tone map tested here compresses the range of the whole scene. None targets contrast at the scale objects actually occupy, which is where the failures are.

44

Found a silent downscale, and fixed it

torchvision shrinks its input so the short side is 800 pixels unless told otherwise, so every 1280×1280 image had reached the network at 800×800. Raising that to 1280 gave +0.4 mAP (31.3 to 31.7), +3.7 AP50, and small-object AP from 6.2 to 8.9. It is now --min_size, stored in the checkpoint so evaluation cannot disagree with training.

45

Retuned the anchor boxes — a better fit that scored worse

85% of objects here are taller than wide (median height/width 2.39), while the detector's stock box shapes stop at 2. Retuning them raised the share of objects the anchors can reach from 82.9% to 96.0%, but mAP fell from 31.7 to 30.4: more objects found, looser boxes. Keeping the native aspect ratio instead of squashing to a square gave 31.4.

Result

Resolution, aspect ratio and anchors all land within 1.3 points of each other. Input geometry is not what limits this model, which agrees with Step 43.

Measured what the module costs

Behind the same RetinaNet, training took 11.3 GB and 55 minutes with the module, against 3.3 GB and 15 minutes with Reinhard. The module works on the full 1280×1280 float image before the detector shrinks it; a fixed tone map is computed once, offline.
